# 重构为微信小程序计划
本计划将现有基于 React + Firebase 的网页应用重构为微信小程序，实现文档中定义的 7S 现场评分、红黑榜、数据分析、历史查询与导出等能力，并完成登录、存储与数据模型迁移/兼容。

## 1. 现状梳理（已完成初步调研）
- **前端形态**
  - React + React Router（`Home`/`Score`/`Analytics`/`History`）+ TailwindCSS + Recharts。
  - 底部导航由 `Layout.tsx` 实现，四个入口：`首页-评分-分析-历史`。
- **后端与数据**
  - Firebase Auth：Google 登录（`loginWithGoogle`）。
  - Firestore：
    - `departments`：部门及房间列表（`Score.tsx` 若为空会自动 seed 默认数据）。
    - `inspections`：评分记录（`date`、`department`、`room`、`totalScore`、`details`、`createdAt`、检查员信息等）。
  - Firebase Storage：照片上传，保存 downloadURL 到 `details.images[]`。
- **关键业务规则**
  - 7 个评分项，分值选项：10/8/4/2。
  - 当单项 `score <= 4` 时，**必须上传照片或填写备注**。
  - 首页红黑榜：按 `totalScore` Top3/Bottom3。
  - 历史页：按月筛选 + 搜索（部门/检查员/日期），支持导出 CSV（含 BOM）。
  - 分析页：从 `inspections` 拉全量数据，在前端聚合生成折线/柱状/雷达图。

## 2. 需要你确认的关键决策（决定实现路线与工作量）
- **[决策A] 技术路线选择**（二选一，建议优先 A1）
  - **A1 原生微信小程序 + 微信云开发**：最贴合文档第 4 章推荐架构，登录、存储、数据库、云函数都在微信生态内，后续发布与权限管控更顺。
  - **A2 跨端框架（Taro/uni-app）**：可复用部分 TS/React 思维或组件，但仍需替换 Firebase/路由/图表/上传等实现；同时引入框架与构建链路复杂度。
- **[决策B] 数据后端选择**（二选一）
  - **B1 迁移到微信云开发（CloudBase）**：建议。用云数据库存 records，云存储存图片，云函数做排行/聚合，减少前端拉全量。
  - **B2 继续使用 Firebase**：小程序端可通过 REST/自建中转服务访问，但会涉及鉴权、跨域/安全、网络稳定性与合规风险；整体复杂度更高。
- **[决策C] 角色与权限**
  - 是否需要区分“检查员/管理员/部门负责人”权限？如果需要：
    - 需要一个用户角色表（如 `users` 集合）或在微信用户表中维护角色字段。
    - 需要云函数/安全规则限制：谁能看全量、谁只能看本部门、谁能导出。

### 2.1 原生小程序 vs Taro/uni-app：差异对比（给你做技术路线选择用）
- **开发范式**
  - **原生小程序**：`wxml/wxss/js/ts + Component/Page`，直接使用 `wx.*` 与云开发 SDK，贴近平台能力。
  - **Taro/uni-app**：用 React/Vue 写页面，编译到小程序；生态更“Web 化”，但最终仍受小程序运行时约束。
- **对平台能力的支持度与稳定性**
  - **原生小程序**：对 `chooseImage`、`uploadFile`、授权/登录、分享、订阅消息等能力支持最及时、最稳定；踩坑最少。
  - **Taro/uni-app**：大部分能力可用，但遇到边缘能力/新能力时可能需要写平台特定适配或等待框架升级。
- **组件与 UI 复用**
  - **原生小程序**：UI 需要按小程序组件体系重写；能更好适配 `rpx`、分包、setData 性能模型。
  - **Taro/uni-app**：如果你已有大量 React/Vue 组件资产，复用收益更大；但本项目现有是 React + Tailwind（依赖 DOM/CSS），直接复用空间其实有限。
- **图表（Analytics）实现**
  - **原生小程序**：通常用 ECharts 小程序版或 canvas 图表库；需要改造 `recharts`。
  - **Taro/uni-app**：也不能直接用 `recharts`（仍是 DOM/SVG 体系），多数情况下依旧要换成 ECharts 或小程序图表库。
- **工程复杂度与调试体验**
  - **原生小程序**：构建链路最短，排障更直接；微信开发者工具体验最佳。
  - **Taro/uni-app**：引入编译器/运行时适配层，构建与调试链更复杂；但多人协作/跨端扩展时更“工程化”。
- **发布与体积/性能**
  - **原生小程序**：更容易做到体积小、性能可控（配合分包与云函数聚合）。
  - **Taro/uni-app**：会引入一定运行时与编译产物体积；性能可达标但更依赖工程优化。

### 2.2 结合本项目的推荐
- **推荐优先选 A1 原生小程序**：
  - 本项目核心是“表单 + 拍照上传 + 云存储 + 榜单/聚合”，原生能力足够且更稳定。
  - 现有 React + Tailwind + Recharts 难以直接复用到小程序（DOM/CSS/图表体系差异大），选跨端框架的复用收益不高。
  - 你已确认后端采用 **B1 微信云开发**，原生方案集成最顺、坑最少。

### 2.3 你已确认的决策记录
- **后端**：B1 迁移到微信云开发（CloudBase）。
- **权限**：不需要区分角色权限。
 - **技术路线**：A1 原生微信小程序。

## 3. 目标架构（以 原生小程序 + 云开发 为主线）
- **小程序端**
  - `pages/home`：红黑榜 + 入口。
  - `pages/score`：评分表单（部门/办公室级联、7 项打分、拍照/备注校验、实时总分、提交成功页）。
  - `pages/analytics`：分析（趋势/对比/雷达）；若性能压力大改为云函数聚合后返回。
  - `pages/history`：历史查询、详情弹层、导出 CSV（改为生成文件并保存/分享）。
  - `components`：图片上传组件（`chooseImage` + 上传到云存储）、评分卡片、排行榜卡片等。
- **云开发端**
  - 云数据库集合建议：
    - `config_departments`（或沿用 `departments`）
    - `inspection_records`（或沿用 `inspections`）
    - 可选 `users`（角色/部门归属）
  - 云函数建议：
    - `submitInspection`：服务端校验（score<=4 强制备注/图片）、计算总分、落库。
    - `getRankings`：按日期/期次返回红榜/黑榜。
    - `getAnalytics`：返回趋势/部门对比/雷达图聚合数据。
    - `exportCsv`：按筛选条件导出 CSV 到云存储并返回 fileID。

## 3.1 小程序信息架构（tabBar 与页面路由）
- **tabBar（4 个）**
  - `首页`：红黑榜 + 入口
  - `评分`：现场评分表单
  - `分析`：数据分析图表
  - `历史`：历史查询与导出
- **非 tabBar 页面**
  - `评分提交成功`：展示总分与操作（查看详情/返回首页/继续打分）
  - `记录详情`：在历史列表点击进入（或用弹层实现）
  - `黑榜扣分项`：可做成弹层或独立详情页（查看照片与备注）

## 3.2 建议目录结构（原生小程序，TypeScript）
- `miniprogram/`
  - `app.ts` `app.json` `app.wxss`
  - `pages/`
    - `home/` `score/` `analytics/` `history/`
    - `score-success/`（非 tabBar）
    - `inspection-detail/`（非 tabBar，可复用到首页黑榜弹层的跳转版）
  - `components/`
    - `image-upload/`（选择图片+上传+预览+删除，最多 3 张）
    - `score-item-card/`（单项打分卡片：四个分数按钮+备注+图片区）
    - `rank-card/`（红黑榜卡片）
  - `services/`
    - `cloud.ts`（云函数调用封装）
    - `db.ts`（集合读写封装）
  - `utils/`
    - `date.ts` `csv.ts`（仅放工具函数）

## 3.3 云开发资源清单（需要在微信开发者工具中创建/配置）
- **云环境**：1 个环境即可（测试/生产可二期拆分）
- **云数据库集合**
  - `departments`：部门与房间配置（沿用现有命名以降低迁移成本）
  - `inspections`：检查记录（沿用现有命名）
- **云存储目录**
  - `inspections/`：按日期或记录 id 分层存放图片
- **云函数**
  - `submitInspection` `getRankings` `getAnalytics` `exportCsv`
- **权限/安全规则**
  - 因你确认“不区分权限”，默认先做“已登录可读写”（或根据你的内部要求改为“仅企业内部成员可用”）。

## 4. 数据模型与兼容策略
- **字段兼容**
  - 现有结构（网页端）：`inspections` 文档中 `date`、`department`、`room`、`totalScore`、`details[{item,score,images,remark}]`。
  - 小程序端可直接复用字段命名，降低迁移成本。
- **图片存储**
  - 从“存 downloadURL”改为“存 fileID（云存储）+ 临时访问链接”。
  - 若需保留旧数据：可在详情渲染时同时兼容 `http(s) url` 与 `cloud fileID`。
- **历史数据迁移**（可选）
  - 若你已有 Firestore 真实数据，需要一次性迁移到云数据库：提供脚本/工具方案（后续实现阶段细化）。

## 5. UI 与交互落地要点（对照 PRD）
- **评分页**
  - 级联选择器：部门 -> 办公室。
  - 每项四个分数按钮，低分强制“照片或备注”。
  - 校验失败滚动定位（小程序中用 `pageScrollTo` + `selectorQuery`）。
  - 提交成功页：查看详情/返回首页/继续打分。
- **首页**
  - 红黑榜卡片；黑榜可点击展开扣分项照片与备注（小程序用弹层/页面跳转）。
- **分析页**
  - 小程序端图表可用：
    - 方案1：ECharts for WeChat（推荐）
    - 方案2：将图表改为列表/简化可视化
- **历史与导出**
  - 小程序无法直接像浏览器那样下载 Blob；导出建议：云函数生成 CSV -> 云存储 -> 小程序端 `downloadFile` / `openDocument` / 分享。

## 6. 实施里程碑（确认决策后进入编码）
1. **确定技术路线与后端**：完成 A/B/C 决策，锁定目标架构与数据集合命名。
2. **搭建小程序工程骨架**：tabBar/页面/组件目录、云开发初始化、基础 UI 复刻。
3. **实现评分闭环**：部门配置读取、打分校验、拍照上传、提交入库、提交成功页。
4. **实现首页/历史/分析**：排行云函数、历史查询与详情、分析聚合与图表渲染、CSV 导出。
5. **权限与安全规则**：用户角色、数据访问控制、云函数校验、上线前自测与性能优化。

## 7. 风险与注意事项
- **Firebase 与微信生态不匹配**：若坚持 Firebase，需要额外中转与鉴权，风险与工作量显著上升。
- **分析页全量拉取性能**：数据量增大后前端聚合会卡顿，建议尽早改为云函数聚合。
- **导出 CSV 的实现差异**：小程序端需走“生成文件 + 下载/打开/分享”的链路。
